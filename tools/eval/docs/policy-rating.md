# 별점·상태 기준 (policy-rating)

> 근거: PRD 「데이터 모델 & 사용자 입력」「별점 입력 계층」「취향 프로필 알고리즘」,
> TODO 「M2.5a 카테고리 설계」「핸드오프 메모(별점 원칙)」.
> 상태 분류의 최종 단계 수와 기피 사유의 집계 방식은 미확정이므로, 확정된 것만 조항으로 두고 나머지는 미확정으로 표기한다.

## 1. 별점 척도

제1조 (척도) 별점은 0.5 단위 5점 만점(10단계, 왓챠식)이다. 플레이타임이 간접 신호(오래 했으니 좋아하나 보다)라면 별점은 직접 신호이며, 둘의 갭(짧지만 별점 높음 = 강렬했던 게임 / 길지만 별점 낮음 = 습관적으로 붙잡았으나 불만족)이 LLM 분석의 정보가 된다.

제2조 (수기 전용) 별점은 수기로만 작성한다. 자동 수집이 값을 매기지 않는다.

## 2. 별점 미입력의 취급

제3조 (평가 없음) 별점은 필수가 아니며 미입력일 수 있다. 미입력은 "0점"이나 "낮은 평가"가 아니라 "평가 없음"이다. 별점은 일부 게임에만 입력돼 있을 수 있다. 미입력임을 밝히는 것이 정답이며, 특정 게임의 별점 유무는 반드시 해당 게임 노트를 조회해 확인한다.

## 3. 상태 분류

제4조 (미확정 표기) 상태 분류의 최종 단계 수는 아직 확정되지 않았다(PRD 열린 질문 #5, 이슈 #8 주관 데이터 스키마 확정). 후보로 거론된 값은 아래뿐이며, 확정 전까지 이 목록을 기준으로 답하되 확정 기준으로 단정하지 않는다.

| 후보 값 | 의미 |
|---|---|
| 플레이중 | 현재 플레이 중인 게임 |
| 완료 | 끝까지 플레이한 게임 |
| 중단 | 그만둔 게임 (`dropped` 집계의 근거) |
| 찜 | 위시·관심 표시 |

제5조 (위시와 보유의 관계) 위시리스트 게임과 보유 게임은 애초에 겹치지 않는 것이 정상이다(이미 산 게임은 위시에서 자연히 빠짐). 위시 ∩ 보유 교집합이 0건이어도 결함이 아니다.

## 4. 찜과 보유의 구분

제6조 (찜은 보유가 아님) 찜(wishlist)은 보유가 아니다. 찜 게임은 플레이타임이 0이고 보유 인덱스(`library.md`)에 포함되지 않으며, 게임 노트만 존재한다(`source: manual`, `wishlisted: true`, `status: wishlist`). 따라서 "그 게임 얼마나 했어?" 류의 문의에 찜 게임이 걸리면 플레이타임을 답하지 말고 보유가 아니라 찜 목록이라는 사실을 먼저 밝혀야 한다.

## 5. 기피 사유 표기

제7조 (dislikeReasons) 기피 사유는 게임 노트의 `dislikeReasons[]` 배열에 키워드로 기록한다. 취향 분석의 명시적 기피 신호로 쓰인다.

제8조 (집계 방식 미확정) 기피 집계의 최종 방식 — rating이 낮으면서 플레이타임이 긴 게임의 장르 집계, `dislikeReasons[]` 키워드→장르 매핑, `status: dropped` 게임 집계 중 세 신호를 합산 점수로 낼지 별도 표기할지 — 는 실제 rating 데이터가 쌓인 뒤 분포를 보고 정한다. 직관으로 임계값을 잡지 않는다.

## 6. 입력 계층

제9조 (코어와 입력의 분리) 별점 "매기기"는 코어 패키지의 책임이 아니라 UI/서버 계층의 책임이다. 코어는 md에 적힌 rating을 읽기·보존·분석·검증하는 헤드리스 계층이며 별점 입력 UI는 없다. 0.5 단위 5점은 클릭 UI가 있어야 성립하므로, 별점 입력은 로컬 서버 + 웹 UI(브라우저의 별 반쪽 클릭 → 서버를 통해 md 저장)에서만 가능하다.

제10조 (CLI만으로 동작) 웹 UI 없이 CLI/코어만으로도 import·분석은 동작한다. 단 별점 매기기는 UI에서만 된다.
